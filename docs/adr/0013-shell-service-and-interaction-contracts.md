# ADR 0013: Shell 按服务契约协作，并验收完整用户任务

- 状态：proposed
- 日期：2026-10-16
- 决策者：架构组与产品负责人（待人类评审）
- 批准记录：待补
- 关系：补充 ADR 0003、0006；若获接受，取代 ADR 0002 决策第 6 条中 wallpaper 直连 compositor 的例外，其余分层不变

## 背景

PRD 原仓库表把 `inox-panel` 等 L3 组件列为依赖 `inox-shell`，`inox-wallpaper` 列为依赖 `inox-compositor`；但根级 AGENTS.md §2/§4 与 ADR 0002 要求组件不横向耦合、合成器与 Shell 通过协议通信。ADR 0002 第 6 条又保留 wallpaper 的特殊边，使表格容易被误当成直接 Cargo 依赖许可。

此外，“面板有时钟/托盘、启动器可以搜索、设置可以写文件”没有定义状态所有权、服务重启、焦点往返或错误呈现。PL-01–PL-03、PL-06、PL-08 的测试/实现显示，应验证模型与交互而非静态外观，见 [Plasma 对照](../quality/plasma-reference.md)。这些证据不要求 Inox 改用 Qt 或复制插件系统。

## 备选方案

| 方案 | 收益 | 代价 / 结论 |
|------|------|-------------|
| 把所有组件链接进一个 Shell 并共享可变模型 | 内部调用方便 | 扩大失败域，违反现有独立组件方向；不采用 |
| 所有 UI 各自查询进程列表、写配置、猜测窗口状态 | 开发起步快 | PID/窗口关系错误、状态漂移、缺少一致的错误语义 |
| 进程边界 + 权威服务 + 快照/事件契约 | 可重连、可替换、可独立测 | 协议维护成本增加；选择本方案 |
| 先建设通用第三方插件平台 | 扩展性高 | 未验证核心任务即扩大加载/权限/兼容面；推迟，另需 ADR |

## 决策

### 职责与依赖

| 组件 | 权威职责 | 消费/请求边界 |
|------|----------|----------------|
| `inox-compositor` | 窗口、工作区、输出、焦点、锁定状态 | 标准 Wayland；必要时经评审的 `inox-ipc` |
| `inox-shell` | 桌面交互协调、跨入口的导航规则 | 服务与协议协作，不作为各 L3 二进制必须链接的“大型 UI 库” |
| `inox-panel` | 面板/任务视图/托盘呈现 | 订阅窗口状态；StatusNotifierItem/DBusMenu；请求激活，不猜 PID 状态 |
| `inox-launcher` | XDG 应用索引、搜索与启动交互 | desktop entry 解析、进程/标准激活边界；结果验证不只看 click |
| `inox-settings` | 草稿、校验反馈、应用/取消/默认值交互 | 配置模型与各服务应用回执，见 ADR 0014 |
| `inox-wallpaper` | 壁纸资源加载与显示 | layer-shell 客户端；不消费合成器内部渲染类型 |
| `inox-notifications` | 通知协议、ID/寿命/队列与显示 | 标准通知 D-Bus 接口，锁定状态下隐去敏感正文 |
| `inox-session` | 进程监督与 ready/退出依赖 | 运行时依赖图，见 ADR 0015 |

L3 组件不建立到其他 L3 仓库或 `inox-compositor` 的新 Cargo 依赖。共享数据只在既有 L1 的真实职责范围内提供，不能把 UI 运行时塞进 `inox-common` 规避分层。需要共享 UI crate 或新仓库时另写 ADR；本提案不批准新的通用框架。PRD 的依赖列须区分 Cargo、协议与进程协作；接受后同步修订 ADR 0002 状态关系与仓库级约束。

### 跨进程状态契约

1. 每类状态只有一个权威来源；客户端连接后先取快照再订阅变化，服务重启/代次变化后丢弃旧视图并重新同步。窗口使用服务端 ID 与会话代次，不能只用 PID、标题或列表索引。
2. 命令明确区分 sent、accepted、applied、rejected/timeout；失败包含可诊断原因。设置显示成功、任务栏切换激活态都以实际结果/回读为准，不把乐观 UI 当权威状态。
3. 重复命令、事件乱序/丢连接、客户端对象销毁都需测试；去重、请求关联、快照/事件的竞态必须在具体协议设计中定义。当前 `inox-ipc` v1 没有这些通用能力，不得假定已支持；若需扩展，先在 `inox-protocols` 定义 XML/版本/授权并评审。
4. I/O、搜索与图像解码不阻塞交互循环。查询结果有请求代次和有界队列，旧搜索结果不能覆盖新词；服务不可用呈现可操作错误与重试，不能一直 loading。

### 交互、可访问性与主题

- 每个组件坚持 Iced 的 Message → update → view；异步结果回到 update，避免后台直接改 UI 状态。
- 展示操作、显式激活、键盘导航分别处理。入口打开时保存有效返回目标，Esc 逐层关闭并返回；原目标已销毁时按合成器焦点策略回退，不向无效对象投递。
- 正常、加载、空、错误、禁用、重试均是需要设计/测试的状态；长标题、缺图标、服务断连、低分辨率及字体放大不能使关键动作不可达。
- 主题只消费令牌；高对比与减少动态偏好是语义令牌/偏好，不在组件内部增加魔法颜色或时长。新增令牌经 `inox-config` 管理默认值与演进。
- 用户文案走 Fluent；从 M4 起以 en-US/zh-CN 的核心任务和语义 role/name/state/action 作为最低交付，完整辅助技术生态仍可后续扩展。语义树必须实际导出并能被读取，不能以类型/空接口存在替代。
- M4 前分别做最小 Iced layer-shell、输入/焦点、AT-SPI 语义导出和 GUI 自动化原型，在 CI 证明可行。驱动和框架缺能力必须作为阻塞/上游工作登记；不能默认 Weston 或 waydriver 已覆盖全部能力。

## 验收与迁移

采用 D01–D06、Q01–Q03、W05、O02–O03、S05。E2 在具备所需协议的隔离宿主上验证组件，E3 在 Inox 会话里完成“搜索→启动→任务出现→切窗→设置生效→服务重启后状态恢复”。修复焦点/状态缺陷要有可复现回归用例与视觉/语义证据。

先澄清依赖清单，再实现最小快照/命令契约和原型；不把组件骨架的 `inox-shell` 文档关系变成 Cargo 链接。若已存在实际依赖，迁移必须上游发布 tag、下游更新、集成验证，不能在本元仓库 PR 中暗改其他仓库。

回退以锁定组件组合为单位，旧客户端遇到新能力应明确显示不可用；破坏性协议不沿用同名旧语义。正式批准前继续遵守既有硬性规则，不根据本 proposed 文件实施未经批准的架构变更。

## 后果

正面：错误和重连路径有权威状态可核实，Shell 崩溃不带走应用；消除 wallpaper 例外与 L3 依赖歧义；可访问性与交互质量在首个 Shell 里程碑得到证明。

负面：需要协议/模型同步与更多真实客户端测试；Iced/语义桥能力可能成为排期关键风险；暂缓通用插件平台会降低初期定制广度。

影响面：PRD §2/§3/§9/§11/§13、ADR 0002 第 6 条、L3 各组件、`inox-protocols`、`inox-config`、`inox-session` 和集成仓库。根级硬性规则不放宽。

复审条件：核心任务需要新的共享 UI 库、可信第三方插件、跨进程共享大对象或无法满足交互预算时，以真实瓶颈和原型证据重审，不默认合并进程。
