# ADR 0010: 版本号语义与发布流程

- 状态：proposed
- 日期：2026-10-16
- 决策者：架构组

## 背景

PRD §3.3 规定了「每个仓库独立发布」「使用 `cargo-release` 打 tag，格式 `vX.Y.Z`」「版本兼容由 `compat.toml` 维护」，根级 `AGENTS.md` §8 规定了跨仓库依赖必须锁定 `tag` 与升级顺序，但三处都没有规定：**什么时候**发版、**为什么**是某个版本号、以及 0.x 阶段的版本号该怎么走。缺了这层，每个仓库只能凭直觉挑号。

这个缺口已经造成过一次实际争议：`inox-common` 新增公开模块 `paths`（纯新增、无破坏性、无既有 API 变化）时，版本从 `0.1.0` 升到了 `0.2.0`。一种读法是「新增公开 API = minor」；但另一种（也是本次评审提出的）是 cargo/crates.io 对 `^0.x` 的解析把 **minor 当作不兼容段**（`^0.1` 不匹配 `0.2.x`），因此在 0.x 阶段让一次兼容的新增占用 minor 段，会同时造成两个后果：向下游传递「可能不兼容」的信号（而它其实兼容），以及把有限的 minor 段快速耗尽（0.1 → 0.2 → 0.3…），使真正的破坏性变更失去专属标记。

约束与依据：

- 根级 §8：跨仓库依赖锁定 `tag` 或 `rev`，升级顺序为「上游发 tag → 下游改依赖 → `inox-integration` 验证」。因此版本号是下游**唯一**能读到的兼容性信号。
- 根级 §11.7：AI 不自行合并到 `main`；发布是把改动交付出去的动作，与合并同级。
- 根级 §3.8 与本 ADR 第 7 条：不得重写已发布 tag 的历史（`inox-common` 的仓库 `AGENTS.md` 也已写明）。
- `compat.toml` 由 `inox-integration` 消费，但该仓库要到 M6 才引入跨仓库依赖，因此矩阵目前是**已发布版本登记表**，而不是「已验证组合」——这个区别必须写下来，否则会被误读成兼容性承诺。
- **AI-first 的迭代速度**：本项目由 AI 写代码、CI 是唯一的验证途径（PRD §5.1、根级 §3.1），`main` 一天可以前进十几次；而跨仓库的改动常常需要在正式发布之前先被下游验证（例如 L1 的能力改动同时要改 L2 的依赖声明）。因此版本号与 tag 的职责必须分清：**版本号只表达兼容性信号，tag 只表达「这是一次发布」**，中间状态一律不占用 tag 空间。
- PRD §1.2：1.0 之前不提供完整的无障碍（AT-SPI 全量）、多语言与主题市场能力。组件的能力远未稳定，此时声明 1.0 无法兑现。

考虑过但未被采纳的方案：

- **0.x 也按标准 SemVer：新增 = minor、修复 = patch**（即本次争议中的现状做法）：与 cargo 对 `^0.x` 的解析不一致，且会在 0.x 阶段把 minor 段耗在兼容变更上，破坏性变更失去专属标记；下游把 `0.1 → 0.2` 读成「可能破坏」而实际兼容，等于浪费兼容矩阵的表达力 —— 不成立。
- **直接进 1.0，此后按标准 SemVer**：与 PRD §1.2 的非目标冲突，1.0 的承诺（稳定接口、完整无障碍与多语言）当前无法兑现 —— 不成立。
- **不发版，只用 `rev` 锁定提交**：根级 §8 虽然允许 `rev`，但它在发布说明、兼容矩阵与「同一组件被多个下游消费于不同版本」这三件事上不可读；`tag` 是唯一能同时被人类与工具读懂的锚点 —— 不成立。
- **每个仓库自定版本号规则**：直接抵消「兼容矩阵 + 逐层升级」的价值，下游要同时理解三种语义 —— 不成立。
- **让 CI 校验 tag 与版本号一致**：CI 的触发是 push/PR，tag 推送本身不会跑我们的工作流；把「发布」做成 CI 副作用还需要额外权限与密钥设计，收益不抵复杂度。改为流程清单 + 人工检查（本 ADR 第 5 条）—— 不成立（暂缓）。

## 决策

1. **0.x 的版本号语义：minor 是不兼容段，patch 是兼容段。** 在 1.0 之前：
   - 兼容变更（新增模块 / 公开类型 / 字段、新增可选配置字段、修正文档与注释）→ **patch**：`0.1.0 → 0.1.1`；
   - 破坏性变更（删除或改名公开项、改变已有 API 的语义、改变已有字段的默认值或行为、提升 MSRV、改变配置文件已有字段的含义）→ **minor**：`0.1.1 → 0.2.0`，并在提交信息与 tag 说明中标注 `BREAKING CHANGE`；
   - 只修缺陷且不改公开 API → patch。
   理由：与 cargo 对 `^0.x` 的解析语义一致，于是「下游升级前必须读发布说明」这件事只发生在真正不兼容的时候，而兼容升级可以放心机械执行。
2. **1.0 之后改回标准 SemVer**（major 破坏、minor 新增、patch 修复）。转入 1.0 必须单独 ADR，不得由某个组件自行宣布。
3. **版本号与 tag 必须一致，且 tag 为 annotated tag。** `Cargo.toml` 的 `version` 与 tag `vX.Y.Z` 是同一个数字；tag 说明写清「新增 / 修复 / 破坏性」，破坏性必须写明迁移方式。tag 只有三类，用途严格区分：
   - **正式版 `vX.Y.Z`**：唯一可被下游**长期**锁定的类别，语义如第 1 条。
   - **预发布 `vX.Y.Z-<pre>`**（如 `v0.2.0-alpha.1`）：仅当一次跨仓库改动需要在正式发布前被下游验证时使用。tag 说明必须写明它预期成为哪个正式版本。下游可以**临时**锁定预发布，但必须在 PR 中注明「临时依赖，正式版发布后升级」；**任何已发布的组件不得锁定预发布**——已发布物只锁正式 tag，否则「已发布」这个词就失去了含义。
   - **快照：不用 tag 表达。** 临时验证直接锁 `rev = "<sha>"`（根级 §8 允许），不产生 tag；`compat.toml` 也不登记快照。
   理由：AI-first 下中间状态很多，若它们也占用 tag 空间，「哪个 tag 是真正的发布」会被噪声淹没；三类分开后，`git tag` 列表本身就等于发布历史。
4. **发布的触发条件（不是每个 PR 都发版）：**
   - 下游需要消费这个能力（例如 L1 的能力被 L2 首次使用）；
   - 某个里程碑的组件侧交付完成，值得给下游一个锚点；
   - 已发布版本中的缺陷被修复，且下游需要该修复。
   `main` 前进不等于版本前进：合并是合并，发布是发布。AI-first 下 `main` 一天可能前进很多次，因此**一个版本通常打包多个 PR**：发布是给下游一个稳定的锚点，不是给每次合并记账。版本号不表达改动量或努力程度，只表达兼容性信号——patch 号涨得快是预期现象，不需要为了「显得更快」而提前用掉 minor。
5. **发布流程（依序执行，缺一不可）：**
   1. 在组件仓库提 PR 更新 `Cargo.toml` 的 `version`（README / `AGENTS.md` 里的版本表述一并更新），走正常 review 与 CI；
   2. 合并后，在 `main` 对应提交上打 annotated tag 并推送；
   3. 在元仓库 `compat.toml` 的 `[components]` 登记该组件的新 tag（组件间版本允许不同步，见第 8 条）；
   4. 需要下游消费时，在对应仓库开「升级依赖」PR：锁定新 tag、显式声明 `version`（`deny.toml` 的 `[bans] wildcards = "deny"` 要求）、若是该仓库首次引入该 git 源则同步登记 `[sources] allow-git`。
6. **谁执行：** 合并到 `main` 由人类执行（根级 §11.7）。打 tag 默认同样由人类执行；AI 只有在**针对某次具体发布**获得明确授权时才能推送 tag，且只能推送人类已合并的提交，不得自行决定版本号。删除或移动 tag 只允许一种情形：该 tag 未被任何已发布组件引用，且人类明确批准（见第 10 条的过渡）。
7. **tag 不可变。** 已被任何已发布组件锁定的 tag 不重写、不移动、不删除。发布后发现缺陷：发新的 patch，不改旧 tag；若缺陷属于破坏性范畴，则按第 1 条走 minor 并说明。这是根级 §8 与仓库 `AGENTS.md` 中「不要在已发布的 tag 上重写历史」的一般化。
8. **`compat.toml` 的语义是登记，不是验证。** `[components]` 记录**各组件当前发布的最新 tag**；它不表示这些版本组合已被集成验证（`inox-integration` 到 M6 才引入跨仓库依赖）。版本不一致时以各下游仓库的 `Cargo.toml` 为准；矩阵用于回答「这个组件现在有哪些版本存在」。**只登记正式 tag，不登记预发布与 `rev` 快照**（见第 3 条）：矩阵是发布历史的名录，不是依赖状态的快照。`[meta] version` 在元仓库自身的发布物（文档索引、矩阵快照）发生实质变化时递增，与组件版本无关。
9. **MSRV 与 edition。** 提升 `rust-version` 属破坏性变更（按第 1 条走 minor），必须在 tag 说明与 PR 中写明理由与受影响的下游；edition 变更同理，且必须单独 ADR（升级前先在 `inox-integration` 验证的流程见根级 §8）。
10. **过渡。** 本 ADR 之前唯一一次按旧习惯的发布是 `inox-common v0.2.0`（新增 `paths` 模块，无破坏性）。按本规范它应记为 **`v0.1.1`**。由于它发布不足一天、且没有被任何**已发布**组件引用（`inox-compositor` 仍锁定 `v0.1.0`，`inox-config` 尚未发布），决定重切：
    1. `inox-common` 的 `version` 由 `0.2.0` 改为 `0.1.1`（含 README / `AGENTS.md` 中的版本表述），合并后打 `v0.1.1`；
    2. 删除 `v0.2.0`（在 `inox-config` 改指 `v0.1.1` 之后执行，确保删除时刻没有任何引用）；
    3. `inox-config` 的 git 依赖与 `deny.toml` 注释改为 `tag = "v0.1.1"`、`version = "0.1"`；
    4. 元仓库与本 ADR 之外引用 `v0.2.0` 的文档（ADR 0009、`inox-docs` 的配置与依赖章节）同步改为 `v0.1.1`。
    此后再无例外，第 7 条一律适用。

## 后果

正面：

- 下游锁定的版本段与 cargo 的解析语义一致：`0.1.x` 内的升级可以机械执行，`0.2.x` 出现则意味着必须读发布说明并做适配。
- 0.x 阶段的 minor 段被留给真正的破坏性变更，不会因为「加了一个模块」而消耗，兼容矩阵与下游 pin 的表达力得以保持。
- 发布从「合并的副产品」变成一个有条触发条件、有责任人、有清单的动作；`compat.toml` 的「登记 ≠ 已验证」被写明，避免 M6 之前被误读。
- 第 3、7 条与根级 §8 形成完整链条：任何时刻都能从 tag 复现某个组合，`inox-integration` 在 M6 可直接以 tag 为输入。
- AI-first 的快速迭代不会污染 tag 空间：中间状态走 `rev` 快照（不产生 tag），跨仓库改动需要提前验证时走预发布（明确标注将被正式版取代），因此 `git tag` 列表始终等于发布历史，`compat.toml` 也始终等于「当前有哪些发布」。

负面：

- 0.x 阶段 patch 号增长较快（`0.1.1`、`0.1.2`…），读者必须知道其中的「新增」也走 patch；因此 tag 说明与发布说明里「新增 / 修复 / 破坏性」的区分不是装饰，而是规范的一部分。
- 每次发布多一个「改版本号的 PR」，比「合并后顺手打 tag」慢一步。
- 第 10 条的过渡要跨仓库改多处（`inox-common` 版本号与 tag 重切、`inox-config` 的 pin、ADR 0009 与 `inox-docs` 的引用），属一次性成本，且删除 tag 需要人类明确批准。
- 本 ADR 只约束「怎么发」，不解决「该不该现在发」（第 4 条给出触发条件，判断仍在人）；判断失误的代价由第 7 条的不可变性兜住，但也意味着错误只能靠新版本纠正。
- 三类 tag 与「临时锁定必须在正式发布后升级」的纪律带来协作成本：预发布与 `rev` 快照都属于**待偿还的债**，下游 `Cargo.toml` 里会留下需要拔掉的钉子。因此第 3 条把「已发布组件不得锁预发布」写成硬约束，并要求临时锁定的 PR 自己写明升级条件。
- 0.x 语义与多数 Rust 生态项目的直觉（新增即 minor）不同，新贡献者与 AI 代理需要先读本 ADR；因此 PRD §3.3 与 `compat.toml` 顶部都加了指向本文件的说明。

影响面：所有组件仓库的 `Cargo.toml` 版本号与 tag 习惯（含预发布与 `rev` 快照的使用纪律）；根级 `AGENTS.md` §8 的升级流程（文字不变，本条在其下补一层版本语义）；`compat.toml` 的登记语义；`inox-docs` 的开发章节；`inox-integration` 在 M6 按 tag 复现组合的能力；以及 `inox-common`/`inox-config` 的一次性过渡。

取代条件：转入 1.0（第 2 条），或需要引入预发布通道、长期支持分支等策略时，新写 ADR 取代本文件；届时本 ADR 状态改为 `superseded`，不删除、不重写。
