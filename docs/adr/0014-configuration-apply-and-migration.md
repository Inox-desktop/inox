# ADR 0014: 配置应用、持久化与升级迁移具有失败原子性

- 状态：proposed
- 日期：2026-10-16
- 决策者：架构组（待人类评审）
- 批准记录：待补
- 关系：补充并修订 proposed ADR 0009 的应用/路径/主题回退约束；TOML、serde/default、L1 所有权与 Fluent 原则不变

## 背景

ADR 0009 的 `ConfigStore` 原子换 `Arc` 只保证进程内配置快照替换，不能保证 DRM mode、输入键位或主题资源已经应用成功。设置 UI 写完文件、收到 reload 请求回执，也不能等同于用户看到的效果已生效。原提案对缺失令牌统一继承深色默认值，可能令不完整浅色主题失去可读性；词法拒绝 `..` 也不能独自防止符号链接逃逸。

PL-06 的服务端回读、PL-07 的历史配置迁移与 PL-05 的无屏时不保存提供了需要保护用户偏好的实例，见 [Plasma 对照](../quality/plasma-reference.md)。本提案自行定义 Inox 的原子写入与回退要求，不把上游迁移脚本视为已实现同等保证。

依据：PRD §9、§13；AGENTS.md §7.1、§8；[验收规范](../quality/acceptance.md) C01–C04、D04、O03。

## 备选方案

| 方案 | 收益 | 代价 / 结论 |
|------|------|-------------|
| 写文件后广播 reload，界面立即成功 | 实现简单 | 消费方可能拒绝、未响应或仅部分生效；不采用 |
| 在 L1 建立跨进程分布式事务服务 | 强一致表述直观 | 引入事件循环/IPC 越层和恢复复杂度，超出需求；不采用 |
| L1 解析/迁移，消费方应用，写入方维护持久化边界 | 边界清楚、失败可测试 | 需明确“已保存”和“已生效”，选择本方案 |

## 决策

### 数据与版本所有权

- `inox-config` 持有 schema、默认值、校验、路径策略与纯迁移逻辑；不依赖 L2 IPC、Iced、calloop 或设备 API。消费者持有自己的生效代次与设备状态；设置是写入/协调方，不能成为所有服务运行的必需中心。
- 首次破坏性格式变更前引入显式 schema 版本，旧无版本配置按初始版本解析；具体字段名/序列化形式须在 `inox-config` 格式 PR 与 ADR 0009 协同评审，未接受前不得擅自部署。新增字段仍给默认值，未知字段仍报错；新版本配置被旧程序明确拒绝，不静默丢字段重写。
- 配置文档区分默认值、用户偏好、运行时设备状态与可重建缓存；缺屏、服务临时不可用不删除偏好。默认缺文件与用户显式选择的资源缺失必须区别：首次默认文件不存在可正常用默认值，指定主题丢失必须报告。
- 自定义主题缺失的令牌按其已解析的 light/dark 外观继承对应默认值；两种外观均做对比度/可读性验证。该规则拟替换 ADR 0009 的“一律深色”行为，需格式/视觉迁移说明，不能悄悄改变已发布主题含义。

### 解析与应用

1. 接收请求后读取完整候选快照，完成语法、字段范围、跨字段与资源校验。错误含文件、行号、字段路径；运行时设备应用错误含配置字段与设备原因，不编造源码位置。整个候选未通过时不发布部分新快照。
2. 消费者先准备新状态，必要设备操作成功后才推进生效代次；中途失败恢复旧资源/旧代次并返回失败。无法立即恢复时报告明确退化状态，不假报“保留旧配置”已成功。
3. 并发重载串行化或使用代次比较；过期异步结果不得覆盖较新请求。SIGHUP 可以重复触发，但重载逻辑必须幂等、有明确结果和限流/合并策略。
4. 跨组件应用以每组件结果呈现，不承诺不存在的全局原子性。设置显示 saved/applied/pending/rejected 的差别；需要协同变更时先校验全部参与方、失败进行可观察的补偿并列出未恢复项。
5. 需要应用回执/关联 ID 的 IPC 扩展先在 `inox-protocols` 按 ADR 0006 评审和版本化；现有 `inox-ipc` v1 的 `config_reloaded` 不能自动承载任意多组件事务。设置关闭后设备确认超时与回退仍由服务端执行。

### 持久化与路径边界

- 所有写入方在目标目录内写临时文件，设置合理权限，完整写入并按目标平台执行文件同步、原子替换与目录同步；不能直接截断正在使用的配置。用故障点测试断电/进程退出窗口的可恢复状态，不把 rename 一步等同于所有文件系统的持久化保证。
- 每个目标文件有明确写入所有者/互斥策略；保存前核对读取时的版本/摘要，检测外部编辑冲突并提示重读，不无条件覆盖手工修改。备份不含凭据且不放宽原文件权限。
- 现有相对路径校验继续拒绝空值、绝对路径、`..`；补充目录 FD/规范化目标的边界检查或等价安全打开策略，防止符号链接跳出根目录与检查后替换。涉及不存在目标/原子写入时按父目录边界处理，不能仅在读前 `canonicalize` 后放任竞态。实现优先安全 API，不能为便利扩张 unsafe。
- 此边界防止配置解析器意外越界，不宣称能隔离已经控制同一用户账号或配置目录的攻击者；仍须防恶意外部主题资源与沙箱应用通过特权服务获得额外能力。

### 升级与回退

- 每个受支持旧版本提供默认/用户定制 fixture，迁移是确定性版本转换，验证幂等、连续多版本升级与中断重试。
- 迁移先备份原件、验证候选，再原子提交；失败保留原件并报告。用户已有选择不因默认值变化被覆盖，未指定的新字段使用新版本默认值。
- 回退文档明确可读版本、备份位置与恢复步骤；不支持反向转换时恢复原备份，不承诺自动无损降级。运行时混装版本必须通过兼容组合检查，不能依赖旧程序忽略新字段。

## 验收与实施顺序

先在 `inox-config` 验证 C01/C04 的纯逻辑，再由真实消费者接入 C02，由设置/写入方接入 C03/D04；显示试用回退与 O03 联测。测试涵盖解析失败、应用失败、只读/磁盘满、并发编辑、符号链接、rename 前后中断、迁移重复执行。

新 schema/主题规则在实现前获得人类批准；上游发布 tag 后下游升级，最后由 `inox-integration` 验证整套组合。初期可不提供跨组件一次性应用，但必须准确报告每组件结果，不能把未实现能力藏在单一成功提示后。

## 后果

正面：用户配置与实际运行状态可追溯；故障不会轻易损坏偏好；配置升级可验证，主题与路径边界更可靠。

负面：保存/应用/补偿流程复杂，需要文件系统故障注入与历史 fixture；部分注释/格式的保留需要具体写入实现评估，不能承诺 serde 重写天然保留；不同文件系统的崩溃持久化能力仍需明确支持范围。

影响面：`inox-config`、配置消费方、`inox-settings`、`inox-protocols`、集成仓库、PRD §9 与配置文档。未新增仓库、格式引擎或跨层依赖。

复审条件：引入远程配置、多用户管理、密钥存储或真正必须跨进程强一致的事务时另写 ADR；不能把当前局部失败原子性当分布式提交保证。
